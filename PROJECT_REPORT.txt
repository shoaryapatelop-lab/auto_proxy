1. PROJECT OVERVIEW
================================================================================

AutoProxy is a Windows desktop application (.NET 8 / WPF) that automatically
detects the current network environment and switches between direct internet
access and a configured proxy server. It monitors network changes, tests
connectivity, applies the optimal proxy configuration to the Windows system
proxy settings, and runs a background health-check loop to handle failures.

7. KEY DESIGN DECISIONS
================================================================================

  - Clean separation: Core has zero Windows dependencies; Windows layer handles
    all P/Invoke; Data layer handles SQLite; App layer handles WPF + DI.
  - All services registered as singletons (no request scope needed).
  - System proxy managed via both WinINet (registry + binary blobs + broadcast)
    and WinHTTP (netsh) for maximum application compatibility.
  - Crash recovery: proxy snapshot persisted to disk; on restart, if the proxy
    settings AutoProxy left behind are still active, they are restored.
  - Network identity is a SHA-256 hash of interface kind + identifier (SSID or
    gateway/subnet), enabling automatic network profile matching.
  - Proxy testing sends requests through a SocketsHttpHandler with WebProxy set
    to the candidate proxy, probing configured 204 endpoints.
  - Captive portal detection looks for redirects and HTML login page keywords.
  - Credential storage uses Windows Credential Manager with DPAPI file fallback.
  - Hysteresis (RetryPolicy) prevents rapid mode switching: health checks must
    fail N consecutive times before triggering a full re-detection.
  - Stale-result protection: new network change events cancel in-flight
    detections so the newest result always wins.
  - Logging automatically redacts credentials (user:pass@ patterns).

8. DETECTION & APPLY RELIABILITY IMPROVEMENTS (2026-09-18)
================================================================================

Detection pipeline
-------------------
  INetworkMonitor (NativeNetworkMonitor)
      -> BuildIdentity: stable SHA-256 identity; WiFi uses SSID (or gateway+
         subnet fallback when SSID is unknown); Ethernet identity EXCLUDES the
         DHCP gateway (lease can change) and uses interface ID + subnet only.
  DetectionEngine
      -> probes direct connectivity (ConnectivityTester)
      -> if direct fails: ranks candidates via ProxyRanker and tests in order
      -> DecisionEngine pick state, produces Reason with failure cause
  ProxyRanker (NEW)  [Detection/ProxyRanker.cs]
      -> deterministic scoring: preferred +2000, recent success 500/350/150,
         success-rate x200, failure count -6, recent failure -80,
         latency +90/+45/+15; ties resolved by latency then id.
  ConnectivityTester (NEW classification)
      -> each probe classified: Healthy, RedirectedToLogin, LoginPageContent,
         ContentMismatch, HttpError, Timeout, DnsFailure, TlsError,
         ConnectionFailed, Cancelled
      -> retries transient failures once (250 ms; timeouts, DNS, 5xx/429)
      -> HTTP 511 treated as captive portal; portal keywords include "log in"
  DirectTestResult (NEW)
      -> FailureReason: None/Offline/ContentBlocked/CaptivePortal/DnsFailure/
         TlsFailure/Timeout/ConnectionFailed/TestCancelled, plus DiagnosticSummary
  DetectionResult diagnostics
      -> carries DirectTest + ProxyTests payload for UI/tests/history

Apply pipeline (NEW)
-------------------
  ApplyEngine (Apply/ApplyEngine.cs) between DecisionEngine and IWindowsProxyManager:
      desired state -> snapshot -> apply -> 300 ms settle -> read-back verify
      -> (proxy only) traffic verify via IProxyTester -> commit
      Any failure -> RestorePreviousSettings rollback
      Disable paths (Direct/Offline/CaptivePortal) skip traffic verify to avoid
      state flapping; disable is read-back verified only.
      VerifyProxyAfterApply setting (default true) gates the traffic check.
  MonitoringService
      -> detection-driven applies route through ApplyEngine
      -> apply failure => ConnectionState.Error + explicit rollback message
      -> Detecting/Error results never touch the system proxy

Windows integration
-------------------
  WindowsProxyManager: GetCurrentSettings now reads AutoConfigURL (PAC/WPAD);
      apply paths never write/clobber it (ownership preserved).
